# Свой сервер и приватность медицинских данных

Документ про один вопрос: где хранить медкарту и что происходит с данными, когда ты задаёшь вопрос ИИ.
Он написан по опыту личного проекта. Это не юридическая консультация.
Для себя и своей семьи схема ниже подходит. Если ты хранишь данные других людей как продукт, это другой проект: нужны согласия, юрист и учёт требований вроде GDPR (медицинские данные относятся к особой категории).

## Три варианта хранения

1. Локально на своём компьютере. Максимум приватности, но нет удалённого доступа и бота.
2. Свой сервер (обычный VPS) плюс бот в Telegram. Данные на твоём железе, доступ отовсюду. Для личного проекта этот вариант выбрали.
3. Сторонний SaaS («операционная система здоровья» с подпиской). Удобно, но данные лежат у чужой компании, и ты не контролируешь, что с ними происходит.

Рынок готовых SaaS занят венчурными компаниями с собственными лабораториями. Соревноваться с ними деньгами бессмысленно.
Свободная ниша — «владей сам»: свой сервер, свои файлы, подгружай что угодно.

Принцип проекта был смягчён один раз и осознанно: не «строго на компьютере», а «своя инфраструктура, данные не уходят третьим лицам».
Оговорка: Telegram и провайдер модели всё же что-то видят. Об этом ниже.

## Что сделали до того, как положили реальные данные

Правило было жёсткое: реальные медданные на сервер только после чек-листа. До этого работали на выдуманных данных.

### Доступ

- Бот отвечает только владельцу. Белый список идентификаторов пользователей Telegram. Всем остальным молчит.
- SSH только по ключу, вход по паролю выключен.
- Службы работают под отдельным пользователем без прав администратора, а не под root.
- Второй фактор (2FA) в боте был реализован как отдельная команда с кодовой фразой. Владелец отключил его, потому что неудобство перевесило. Защитой остались белый список и изоляция сервера. Механизм в коде сохранён, его можно включить обратно. Если ты не готов принять такой компромисс, оставь 2FA включённым.

### Сервер

- Отдельный сервер только под этот проект. Не клади медкарту на машину, где живут другие сервисы: взлом соседа открывает и твои данные.
- Файрвол: наружу открыт только SSH. Бот сам ходит к Telegram, поэтому входящие порты ему не нужны.
- fail2ban против перебора паролей по SSH.
- Автоматические обновления безопасности.
- Веб-страницы (если они есть) — только за паролем и по HTTPS.
- Шифрование диска сознательно не делали. Для арендного VPS это полумера: ключ всё равно оказывается в памяти машины у хостера. Реальную защиту дают хардненинг, изоляция и то, что данные нигде больше не светятся.

### Секреты

- Ключи и токены лежат в файле окружения `.env`, права 600 (читает только владелец).
- `.env` в `.gitignore`. В репозитории только `.env.example` без значений.
- Весь git-репозиторий прогнали сканером секретов (gitleaks). Нашлись срабатывания, но все ложные: сканер принял идентификаторы обследований за ключи. Для таких случаев добавили файл исключений.
- Если ключ однажды попал в репозиторий, считай его скомпрометированным и перевыпусти. Удаления из истории мало.

### Код и зависимости

- Ручной обзор кода бота: нет `eval` и `exec`, ввод пользователя не исполняется как команда.
- Проверка зависимостей на известные уязвимости: `pip-audit` (для Python) или `npm audit` (для JavaScript).
- Статический анализ кода: `semgrep`. Одно срабатывание оказалось ложным: адрес берётся из конфига сервера, а не из ввода пользователя.
- Перед каждой выкладкой изменений кода повторяй проверки.

### Резервные копии

- Решение проекта: на сервере нет уникальных данных, поэтому отдельный бэкап сервера не нужен. Главный файл медкарты лежит в приватном git-репозитории на компьютере, код в git, секреты восстановимы. Сервер поднимается заново по инструкции примерно за полчаса.
- Это работает только пока правда «на сервере нет ничего уникального». Если бот записывает на сервер данные, которых больше нигде нет, делай шифрованный бэкап и проверяй восстановление.
- Исходные медицинские файлы (сканы, PDF) не клади в git. Репозиторий приватный, но сырьё не должно попадать даже туда.

## Что видит поставщик модели

Это самая недооценённая часть. Когда ты спрашиваешь облачную модель, текст запроса уходит поставщику.

- Если в запросе вопрос и выдержки из медкарты, провайдер видит и то, и другое.
- Условия хранения и использования данных зависят от провайдера и тарифа. Читай их сам. Заявления провайдера о том, что данные API не используются для обучения, ты сам не проверишь. Относись к ним как к обещанию, а не к гарантии.
- Облачный провайдер — третье лицо. «Данные не уходят третьим лицам» тут неверно, если ты отправляешь медкарту в облачную модель.

В проекте для этого сделали два слоя.

1. Локальная модель по умолчанию. Без явного разрешения данные с сервера не уходят.
2. Защитный фильтр. Он блокирует вызов облачной модели, пока владелец явно не включил флаг. Облако включается осознанно и обезличенно (например, возраст и диагноз заменяются категориями).

Научная часть проекта (поиск источников, чтение абстрактов) отправляет в облако только публичную науку: общую тему и тексты статей.
Урок: однажды в промпты облачных моделей добавили медпрофиль, чтобы выводы звучали «лично». Ревью поймало это как нарушение главного принципа. Удобство для качества не отменяет приватность.
Проверочный вопрос на каждый внешний вызов: что реально туда уходит?

Ещё одна поверхность утечки — логи.

- Если бот пишет в лог весь исходящий текст, в логе лежат ответы по медкарте. Логируй сознательно.
- Файл лога держи вне git, с правами только для владельца, и ограничь его размер.
- В проекте логирование включили по требованию владельца для разбора ошибок. Это не бесплатно: появился ещё один файл с медицинским текстом.

## Telegram как транспорт

- Telegram — это только канал. Его облако видит сообщения между тобой и ботом.
- Обычные боты не используют сквозное шифрование. Ты принимаешь это, если пишешь боту про здоровье.
- Токен бота — это секрет. Кто его получил, тот может управлять ботом. Держи его в `.env`.
- Сначала сделай, чтобы бот отвечал только твоему идентификатору. В нашем воркшоп-репозитории первый, кто написал боту, становится владельцем. Напиши первым сам и никому не передавай ссылку, пока не убедился в этом.
- Не пересылай боту то, что не готов показать Telegram.

## Чек-лист перед тем, как положить реальные данные

Отмечай пункты по порядку. Если пункт красный, оставайся на выдуманных данных.

Доступ

- [ ] Бот отвечает только владельцу (белый список). Проверено сообщением с чужого аккаунта.
- [ ] Страница с медкартой закрыта паролем и открывается только по HTTPS.
- [ ] Решено, нужен ли второй фактор. Если нет, причина записана.
- [ ] SSH только по ключу, пароль выключен.

Сервер

- [ ] Сервер отдельный, на нём нет чужих сервисов.
- [ ] Файрвол открывает только то, что нужно (обычно только SSH).
- [ ] Включены fail2ban и автоматические обновления безопасности.
- [ ] Службы работают не под root.

Секреты

- [ ] Ключи в `.env` с правами 600. В git только `.env.example`.
- [ ] Прогнан сканер секретов по всей истории git.
- [ ] Знаешь, как быстро перевыпустить каждый ключ.

Код

- [ ] Проверены зависимости (`pip-audit` или `npm audit`).
- [ ] Прогнан статический анализ (`semgrep`).
- [ ] Просмотрено, куда код отправляет данные наружу.

Данные

- [ ] Сырые файлы вне git (`.gitignore`) и не публикуются.
- [ ] Понятно, что в облачную модель уходит и что нет. Для облака решено, что обезличивается.
- [ ] Включено или нет логирование сообщений, и этот файл защищён.
- [ ] Резервная копия есть либо осознанно не нужна (на сервере нет уникального).

Когда все пункты зелёные, клади реальные данные. После любого изменения кода бота повторяй проверки.
